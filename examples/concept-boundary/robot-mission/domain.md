# Robot mission executive

A warehouse inspection robot receives a goal in a named map frame, navigates to an inspection station, and reports completion. The executive coordinates goals and observations; it is not the motor controller. The modeled trace is: revise Mission → record PerceptionSnapshot → request and assess a trajectory → issue a leased MotionCommand → observe the controller receipt. ReviseMission alone owns Mission, including Ready/Executing/Hold/Aborted/Completed; AdvanceMission emits decisions that the owner may admit as transitions. A command acknowledgment is not proof of physical arrival.

Concrete operations are admit/revise/cancel a goal, accept a scene sample, request replanning, reject a stale candidate, renew or stop a command lease, and record a controller refusal. A candidate must match mission revision, scene sequence, coordinate frame and safety-envelope/model digests. A revision change invalidates old candidates, and retries reuse a command sequence. A delayed receipt cannot complete a new mission revision. The proposed mode/safety facet requires Hold on uncertain localization and Stop after lease expiry; only the local controller can enforce the latter while the executive is disconnected.

Unexpected obstacles, an expired plan, solver failure, frame mismatch, motor faults and loss of network connectivity are distinct exceptions. The executive records why progress stopped rather than fabricating physical success. Sensor fusion, trajectory optimization, actuator saturation, friction, contact and braking distance require specialist models and measured verification. This fixture includes no executable safety controller or physical robot.

ConceptIR JSON is a typed information contract. Null/optional selection describes an absent prior mission/receipt, not an execution engine. Operator authorization is a named policy predicate; authentication, current permissions and safe transition enforcement still need a realization. External correlation and mode guards are obligations explained here, not proof supplied by the loader.

Request/admit protocol: AssessPlan accepts an optional candidate. A new-scene activation exports PlanningRequest without emitting PlanAssessment; CandidateReady admits only a response matching missionId, missionRevision, sceneSequence, frame and safetyEnvelopeDigest, then emits assessment without issuing another request. AdvanceMission may run without an assessment to produce Hold/Stop; only a matching assessment permits FollowTrajectory. CommandDecision activates ReviseMission to update mode without changing goal revision; a GoalSpec request changes the goal/revision. Receipt correlation uses (missionId, missionRevision, commandSequence), never sequence alone. These branch and correlation rules are realization obligations; the null behavior bodies do not implement them.
