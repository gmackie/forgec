Composable units on Workers isolates Design · Draft

2026-10-23 · forgec + loom · epics FORG-26, LOOM-11

North star: Loom symbols compile to content-addressed units. Composing a program means linking unit hashes against interfaces derived from domain-ir. Worker isolates run exactly the closure each entry point needs, and deploying is a manifest-hash pointer flip. We get there through two steps: forgec running as WASM, and forgec producing units.

Decisions so far

Vision = symbol-level composition; steps = forgec→WASM, then unitsIterate on each step separately. Neither step is the final goal.
Languages: TS/Effect → JS modules, plus Rust → WASM components, for nowLong-term aim is a Forge-native behaviour language. WASM-everywhere must remain possible.
A unit's format is an attribute of the artifact, never part of its identitykind ∈ js-module | wasm-component | forge-native is metadata. Identity = interface hash + implementation hash + dependency interface hashes, so a body edit re-identifies only that unit. Closure identity covers the resolved unitHashes and pins the exact implementations.
Linking is pluggable; explore strategies in parallelEvery linker consumes the same Closure Manifest and is checked against the same conformance suite.
Capabilities, not envUnits declare capabilities, and the linker injects narrowed handles. This enables sandboxing, maps cleanly to WIT imports, and is the cost of giving up direct env.DB access.

Core model

ConceptDefinition
UnitThe smallest compiled thing. In v1, a forgec function, transition, workflow step or handler plus the Loom symbols it reaches. Later it can be a single symbol. Fields: interfaceHash, unitHash, kind.
InterfaceInputs, outputs, errors, effects and required capabilities, all taken from domain-ir. Structural: the symbol is the binding name, not part of the interface hash, so a JS unit and a WASM unit of the same shape share one. WIT is generated from this, never hand-written and never taken from TS types.
Closure ManifestContent-addressed. Each entry point (route, queue consumer, cron, workflow step or DO class) maps to a root unit plus its resolved dependency closure, capability imports bound to providers, and required bindings. Its closureHash covers the closure's unitHashes, so it changes whenever any implementation it runs changes.
LinkerTurns a manifest into something that runs. A: deploy-time packed scripts. B: a host Worker plus Dynamic Worker Loader, with isolates cached by closure hash. C: A by default, B for closures marked dynamic (previews, Sessions, tenant extensions).

Linker strategies — run in parallel, same contract

A · Packed Start here

  • Uses only stable platform features, easy to test
  • Tree-shaking down to the symbol
  • A one-symbol change still means re-uploading every script that contains it

B · Dynamic

  • Closures load by hash at request time; deploy takes milliseconds
  • Real per-closure capability sandboxing
  • Depends on a newer platform feature, and cold-start behaviour is harder to predict

C · Tiered

  • Production stays predictable, agents get instant iteration
  • Fits Loom's private Sessions
  • Needs A and B both working first

JS ↔ WASM boundary

Workers run core WASM but don't natively support the component model. The linker therefore transpiles components to a core module plus JS glue generated from WIT (jco-style). Calls between JS units are plain imports with no overhead. Values are serialized only when they cross into or out of WASM. Because both kinds share one interface, swapping a Rust unit for a JS unit with the same interfaceHash needs no change in callers.

Scope

Goals

  • One manifest format consumed by every linker
  • JS and WASM units composing through one interface layer
  • Measured budgets for size, cold start and boundary cost
  • Reproducible, content-addressed builds

Non-goals (for now)

  • Changing Loom v1's byte-canonical storage (ADR 0093)
  • Designing the Forge-native behaviour language
  • Compiling TS to WASM
  • Production deploys; these are research spikes

Failure handling & verification

RuleBehaviour
Missing unit hash or interface mismatchFails while the manifest is being resolved, never at request time
Undeclared capabilityNo handle is injected, so the unit fails closed
Dynamic cache miss (C)Falls back to the packed path. The fallback is logged as a fallback, never hidden
Linker differentialThe same manifest under A, B and C must give identical results on the applicable conformance scenarios
ReproducibilityTwo builds produce byte-identical units and manifests
BudgetsRecorded as evidence. If a budget is exceeded, the result is reported as unverified, not as passed

Risks

High forgec has dependencies that can't run on Workers (filesystem, threads, native crates). T1 finds them first. Abstract I/O behind a virtual filesystem fed from Loom or R2.

Medium The Dynamic Worker Loader may be unavailable on our account, or may change. Linker B is a spike, and A works without it.

Medium The cost of crossing the JS↔WASM boundary dominates fine-grained units. T5 measures it, and the planner can merge units that call each other a lot into one closure group.

Open questions

  • v1 unit size: forgec function vs a single Loom symbol. We're starting with function and will revisit after T2 and T6.
  • Whether the manifest should become part of contract.json or stay a sibling artifact.
