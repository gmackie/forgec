Failures reproduced on the original baseline

  • Importer: recursion aborts with stack overflow; a negative numeric bound emits code that fails forgec check; typed maps widen to json without an unsupported-feature entry. Cloudflare’s selected schema reports 50 unsupported features and fails compilation; GitHub reports 23 and compiles with reduced contracts. Issue #187.
  • Inbound recovery: a failed subscription handler is already marked processed; redelivery returns duplicate and the handler runs only once. Reproduced through Engine.consume with MemoryStorage. Issue #188.
  • Cloudflare core isolation: after initializing a second API with the same operation ID, the first instance returns the second API’s response metadata.
  • Generic response handling: success/result business objects are unwrapped and lose sibling fields; success:false becomes CloudflareApiEnvelopeError.
  • Documentation: fern-forge rejects x-forge-kind/x-forge-slo on all 55 operations of our Acme OpenAPI fixture. Keep canonical runtime metadata intact; use a separate optional docs projection.
  • SDK map completeness: GitHub’s array-returning list method has no responseType entry even though its TypeScript return is typed. The map is a call-site join, not a complete type IR.

Decisions and next work

  1. Keep .forge semantics, runtime enforcement and capability identity in ForgeGraph. Treat generated vendor SDKs and their operation maps as replaceable, pinned build artifacts.
  2. Retain explicit domain input/output mappings, host-provided credentials, validation and vendor error policy. The prototype disables SDK retries and reports disconnected writes as uncertain.
  3. Resolve the importer and delivery defects before promising general vendor import or recoverable inbound integrations. Generic upstream reproductions are recorded locally and have not been submitted to maintainers.
  4. Run a bounded sandbox capability pilot (#189) only after those relevant gates pass. Keep the prior transport selectable; compare reads, never duplicate writes. Roll back connector version and backend together and reconcile unknown writes before replay.
  5. Keep polling, webhook verification/checkpoints, cancellation, independent-release matrices and live multi-host certification as explicit outstanding work. These are not inferred from SDK success.

Overview

Investigate how ForgeGraph’s compiler/runtime and Cloudflare Forge can evolve alongside one another. The leading hypothesis is that Cloudflare Forge can supply generated vendor API clients and operation metadata behind ForgeGraph external bindings. SDK and documentation generation for ForgeGraph’s own APIs is a secondary track. This is a research plan, not approval to replace a generator or commit to an upstream dependency.

Scope correction: /Volumes/dev/forge is the compiler/runtime repository. /Volumes/dev/ForgeGraph is the control plane and management UI. It is explicitly out of scope because it may be substantially overhauled. No investigation phase depends on its present implementation. “Cloudflare Forge” always means the upstream OpenAPI tooling project.

Goals & Non-goals

Goals

  • Measure how much handwritten external integration code generation can remove.
  • Prove stable operation identity, correct serialization and explicit semantic mappings.
  • Define ownership between vendor tooling, connector bindings and compiler/runtime.
  • Establish an upgrade and regression process across independently released projects.
  • Produce an evidence-backed adopt, narrow-adopt, defer or reject decision.

Non-goals for this investigation

  • Rewriting the language, runtime, persistence planners or control-plane UI.
  • Automatically treating vendor IDs as local resource references.
  • Assuming an OpenAPI client implements webhook ingestion or synchronization.
  • Replacing all existing SDKs or changing production integrations.
  • Publishing packages, contacting maintainers or deploying trial adapters in this planning task.

A connector definition is a versioned contract plus implementation. A connection is an environment-specific binding and secret references. A capability is the operation the application depends on. A source is a one-way trigger, not a synonym for all external systems. These are proposed investigation terms; reconcile them with existing domain vocabulary before adding public APIs.

Verification and decision criteria

GateRequired evidence
Contract fidelity — mandatory100% coverage of selected operations; no silent schema/operation loss. Golden HTTP transcripts include headers, body and error results. Explicit rejection counts as a documented limitation, not a pass.
Execution correctness — mandatoryDependency checks, response validation, tenant/account isolation, credential redaction and failure classification. Retries respect vendor idempotency; uncertain writes remain uncertain until reconciled.
Host compatibility — mandatory for any claimed profileExecute the generated client through the binding on each claimed host. Node-only proof is not Workers proof. Keep generation tooling out of deployed bundles.
Reproducibility — mandatoryPinned input/spec/overlays/toolchain plus recorded commands and artifact hashes. Two clean generation runs compare after explicitly documented normalization only.
Evolution — mandatoryVendor and generator version changes produce explainable diffs; stable callable IDs survive presentation renames; old version can be restored.
Value — comparativeMeasure handwritten transport removed versus semantic code retained, integration/debug time, patch count, build time, deployed size and update effort. Decide acceptable budgets after baseline measurements; do not invent performance claims.

Run the smallest relevant test sets first. Generator core tests and importer tests establish local behavior; binding transcript tests establish integration behavior; live sandbox checks establish vendor compatibility. Run live writes only with scoped test credentials and explicit sandbox targets. Production rollout is separate work.

Risks & Mitigations

RiskMitigation / decision trigger
“Generic” pipeline embeds Cloudflare assumptions.Non-Cloudflare fixture is mandatory; make provider-specific response behavior configurable or choose another backend.
Our importer and their SDK accept different schemas.Shared compatibility corpus, exact unsupported reports and per-connector capability restrictions; never infer runtime type support from generated TypeScript.
Generated retries compound runtime retries.Assign one retry owner and test acceptance-then-timeout writes. Require vendor idempotency or explicit reconciliation.
Operation-map internals change.Version the binding map, validate all selected entries and retain stable ForgeGraph IDs. Avoid dynamic string evaluation of SDK accessors.
Connection configuration gets mistaken for authorization.Retain existing credential scoping, declared dependencies and policy checks. A generated confirmation hint is not a runtime authorization decision.
Build system mismatch.Measure Docker/Fern requirements against reproducible compiler/runtime build requirements. Consider a dedicated generation job with pinned output; no generator Docker dependency at runtime.
Long-lived fork or license obligations outweigh savings.Audit transitive generator/runtime licenses and patch surface. Prefer supported extension points; retain a backend replacement path.
Name collisions across tooling and metadata.Keep “Cloudflare Forge” and “ForgeGraph” explicit; invoke project-local binaries (their forge versus product forge/fg and compiler forgec). Inventory x-forge-* before any migration.
Active workspaces invalidate conclusions.Pin experiment revisions and content hashes. Re-run affected fixtures after rebasing; do not overwrite ongoing compiler work.

Open Questions

  1. Which external integration is painful enough today to be the second, non-Cloudflare proving case?
  2. Should applications depend directly on selected vendor operations, on stable domain capabilities, or support both tiers explicitly?
  3. Should the first reusable artifact be generated source bundled with an application, or a separately versioned connector package? Start with source until the seam is proven.
  4. Can Cloudflare’s packaged transformer operate generically without custom runtime patches, or is its core framework the better reuse level?
  5. Where should normalized vendor metadata live so the importer and binding generator consume one versioned definition, with optional future tooling able to inspect it?
  6. Does the SDK operation map expose enough information for robust request assembly without coupling to Fern internals?
  7. What minimal connection and credential-provider interfaces let application hosts configure connectors without tying them to a particular control plane or UI?
  8. What host profiles and live-vendor evidence are required before marking a connector supported?
  9. Who owns ongoing upstream compatibility and release monitoring? Proposed cadence: pinned releases, release-triggered candidate runs plus a periodic review; no automatic production promotion.
